'웹 앱'과 '자동화 스크립트'의 차이

웹 앱은 사용자가 브라우저로 접속해서 화면을 보고 버튼을 누르는 등 '상호작용'을 하는 프로그램입니다.

반면, 특정 시간에 자동으로 돌아가는 기능은 화면이 없는 '백엔드 스크립트(또는 배치 프로그램)'의 영역입니다.

왜 '웹 앱'으로 하면 난이도가 올라갈까요?

단순히 데이터만 모아서 시트에 넣으면 되는데, 웹 앱으로 만들면 사용자가 로그인하는 화면, 종목을 등록하는 화면, 웹 서버 호스팅 비용 등 신경 써야 할 과제가 너무 많아집니다. 난이도가 '하'에서 '중~상'으로 급격히 올라갑니다.

가장 추천하는 올바른 방향

구글 앱스 스크립트(Google Apps Script, GAS)를 사용하면 별도의 웹 앱 구축 없이, 구글 시트 자체에 내장된 코드로 매일 특정 시간에 주가를 가져오도록 가장 쉽고 완벽하게 구현할 수 있습니다.

💡 결론 및 제안: > 만약 굳이 웹 화면(대시보드 등)이 필요한 게 아니라면, 유형을 **'구글 시트 내장형 자동화 스크립트'**로 변경하는 것을 강력히 권장합니다. 이렇게 하면 난이도는 **'하'**로 내려가며 목적에 가장 부합합니다. 웹 화면이 반드시 필요한 이유가 있다면 그대로 진행하겠습니다.

3. 핵심 기능 목록 (초안)
구글 앱스 스크립트(GAS) 환경에 맞춰 구성한 기능 목록입니다. 객관적으로 분석하여 분류했습니다.

1) 필수 기능 (MVP - 이것 없으면 프로그램의 의미가 없음)
종목 설정 및 관리: 구글 시트의 특정 영역에 사용자가 주식 종목 코드(예: 삼성전자 005930, 애플 AAPL)를 입력하면 이를 인식하는 기능

주가 데이터 수집 (크롤링/API): 설정된 종목의 당일 종가(Price) 데이터를 외부에서 가져오는 기능

시트 자동 기록 (Appender): 가져온 주가 데이터를 지정된 시트에 날짜와 함께 누적하여 기록하는 기능

시간 기반 트리거 (Timer): 매일 정해진 시간(예: 장 마감 후)에 코드가 알아서 실행되도록 구글 트리거를 설정하는 기능

2) 선택 기능 (추후 확장 가능한 보너스 기능)
알림 기능: 데이터 수집이 성공 완료되었거나, 오류가 발생했을 때 카카오톡이나 이메일(Gmail)로 알림을 보내주는 기능

오류 예외 처리: 주말/공휴일 등 장이 열리지 않는 날에는 실행을 건너뛰거나, 잘못된 종목 코드가 있을 때 에러를 뿜지 않고 패스하는 기능

짚고 넘어가야 할 분석 및 피드백 (오류 잡아내기)
많은 입문자분들이 필수 기능에 "국내 주식과 해외 주식 주가를 실시간으로 가져오기"를 넣고 싶어 합니다. 하지만 여기서 두 가지 치명적인 문제가 발생할 수 있어 바로잡아 드립니다.

국내/해외 주식 데이터 소스의 이원화

구글 시트에는 =GOOGLEFINANCE()라는 강력한 내장 함수가 있습니다. 미국 주식은 이 함수로 실시간에 가깝게 가져올 수 있지만, 국내 주식은 20분 지연되거나 간혹 데이터가 누락되는 고질적인 문제가 있습니다.

따라서 국내 주식을 정확히 수집하려면 네이버 금융 등에서 크롤링(데이터 추출)을 해야 할 수 있습니다.

트리거 실행 시간의 한계

구글 앱스 스크립트의 시간 트리거는 "오후 4시 정각"처럼 정밀하게 세팅할 수 없고, "오후 4시~5시 사이" 같은 시간 범위(Window)로만 실행 지정이 가능합니다. 초 단위의 정밀한 스케줄링은 불가능하다는 제약 사항을 인지해야 합니다.

💡 제안: > 처음에는 복잡한 크롤링 코드를 짜기보다, 구글 시트 내장 함수(=GOOGLEFINANCE)를 활용해 데이터를 가져오는 방식을 '필수 기능'으로 잡고, 이것이 실패할 경우 네이버 금융을 긁어오는 방식을 '선택 기능'으로 돌리는 것이 안전합니다.

1. 주식 데이터 수집 방식 후보 분석
① 구글 시트 내장 함수 활용 방식 (GOOGLEFINANCE)
구글 시트가 자체적으로 제공하는 =GOOGLEFINANCE("종목코드", "price") 함수를 코드(GAS) 내에서 호출하거나 셀에 입력하여 데이터를 가져오는 방식입니다.

장점: 별도의 크롤링 코드가 필요 없고, 서버 차단의 위험이 전혀 없으며, 미국 등 해외 주식은 실시간에 가깝게 완벽하게 가져옵니다.

틀린 부분 바로잡기 (단점): 국내 주식(KOSPI/KOSDAQ)의 경우, 구글 파이낸스 데이터에 20분 지연이 발생하거나 특정 종목의 당일 종가가 정시(예: 오후 4시)에 바로 업데이트되지 않고 누락되는 현상이 종종 발생합니다.

② 웹 크롤링 방식 (UrlFetchApp + 네이버 금융)
GAS의 내장 기능인 UrlFetchApp을 사용하여 네이버 금융 등의 주식 정보 페이지 HTML을 원격으로 긁어온 뒤, 정규표현식이나 문자열 파싱으로 당일 종가를 추출하는 방식입니다.

장점: 국내 주식의 경우, 장 마감(오후 3시 30분) 이후 정확한 당일 최종 종가를 가장 확실하게 가져올 수 있습니다.

단점: 네이버 금융의 웹 페이지 구조(HTML 태그 등)가 변경되면 코드가 작동하지 않아 주기적으로 코드를 수정해야 하는 유지보수 문제가 있습니다.

4. 기술 스택 및 실행 환경 (GitHub Actions 대안 분석)
실행 주체: GitHub 인프라 서버 (Runner)

작동 방식: 1. 깃허브 저장소(Repository)에 주가를 긁어오는 코드(Python 또는 Node.js 등)를 작성해 둡니다.
2. 깃허브 액션스의 스케줄러(Cron Trigger)가 매일 정해진 시간(예: 오후 4시)에 가상 컴퓨터(서버)를 실행합니다.
3. 이 가상 컴퓨터가 코드를 실행하여 네이버 금융에서 주가를 크롤링합니다.
4. 크롤링한 데이터를 구글 시트 API(Google Sheets API)를 통해 내 구글 시트에 원격으로 입력합니다.

비용: 무료 (퍼블릭 저장소 기준 월 2,000분 무료 분량을 주는데, 하루 1~2분이면 충분하므로 평생 무료 가깝게 쓸 수 있습니다.)

짚고 넘어가야 할 분석 및 피드백 (GAS 대비 장단점 교정)
GitHub Actions는 매우 강력하지만, 현재 만들고자 하는 프로젝트 기준으로는 구현 난이도가 몇 배로 상승합니다. 그 이유는 다음과 같습니다.

보안 인증(OAuth2/Service Account)의 장벽 (틀린 부분 바로잡기)

GAS는 구글 서비스 안에서 돌기 때문에 내 구글 시트에 접근할 때 별도의 인증이 필요 없습니다.

반면, GitHub Actions는 '외부 서버'이기 때문에 구글 시트에 데이터를 쓰려면 구글 클라우드 콘솔에서 프로젝트를 만들고, API를 활성화하고, 서비스 계정 키(JSON)를 발급받아 깃허브 비밀키(Secrets)에 등록해야 합니다. 입문자분들이 여기서 가장 많이 포기합니다.

시간 트리거의 정밀도 문제

GitHub Actions의 Cron 트리거는 정밀하게 분 단위 설정을 할 수 있다는 장점이 있지만, 전 세계 수많은 개발자들이 동시에 무료 서버를 쓰기 때문에 스케줄링된 시간보다 최소 10분에서 최대 1~2시간까지 지연 실행되는 일이 빈번합니다. 장 마감 직후 정시 실행을 보장하기 힘듭니다.

제약 사항은 프로그램이 정상적으로 작동하기 위해 반드시 지켜져야 하는 환경적 한계나 규칙을 의미합니다. 이 프로젝트가 GitHub Actions와 구글 API를 사용하기 때문에 발생하는 현실적인 제약들을 명확히 짚고 넘어가야 나중에 예기치 못한 에러로 당황하지 않습니다.

8. 제약 사항 (Constraints)
GitHub Actions 환경의 특성을 반영한 객관적인 제약 사항 목록입니다.

1) 실행 시간의 비정밀성 (Cron 지연)
GitHub Actions의 무료 서버(Runner) 스케줄러는 정시 실행을 보장하지 않습니다. 예를 들어, 한국 시간 오후 4시 정각(0 7 * * 1-5)으로 설정하더라도 실제 실행은 구글/깃허브의 서버 대기열 상황에 따라 오후 4시 5분 ~ 4시 30분 사이에 지연되어 실행될 수 있습니다.

따라서 '초 단위, 분 단위의 칼 같은 정시 실행'이 필수적인 서비스에는 부적합하며, '장 마감 이후 저녁 시간대 중 수집 완료'라는 관점으로 접근해야 합니다.

2) 구글 API 호출 제한 (Quota Limits)
구글 시트 API v4는 계정당 분당 요청 횟수 제한(예: 분당 약 300회)이 있습니다.

프로그램이 다중 종목을 수집할 때, 한 종목씩 시트에 데이터를 쓰고 지우는 방식을 쓰면 이 제한에 걸려 프로그램이 뻗어버립니다. 이를 방지하기 위해 파이썬 코드 내에서 데이터를 배열(배치)로 묶어 단 한 번만 시트에 업데이트(Batch Update) 하도록 구현 언어 레벨에서 제약을 두어야 합니다.

3) 네이버 금융 웹사이트 구조 변경 리스크
우리는 네이버 금융의 공식 API가 아닌 '웹 페이지 HTML을 긁어오는 방식(크롤링)'을 사용합니다. 만약 네이버 금융이 사이트를 대대적으로 개편하여 주가가 표시되는 태그의 이름이나 구조를 바꾸면, 프로그램은 주가를 찾지 못하고 에러를 발생시킵니다.

이 경우 프로그램의 결함이 아니므로, 개발자(본인)가 파이썬 코드의 크롤링 타깃 태그 경로를 직접 수정해 주어야 합니다.

4) 보안 비밀키 관리 (GitHub Secrets)
구글 시트에 접근하기 위한 크레덴셜(credentials.json) 파일이나 이메일 비밀번호를 GitHub 코드 저장소(Repository)에 그대로 올리면 전 세계에 내 구글 계정 권한이 유출됩니다.

모든 인증 정보는 반드시 GitHub 저장소의 Settings -> Secrets and variables 메뉴를 통해 암호화된 환경 변수로만 관리해야 합니다.

GitHub Actions는 장이 열리지 않는 토요일, 일요일에도 오후 4시가 되면 정직하게 작동합니다. 이때 네이버 금융에 접속하면 금요일 종가나 직전 거래일의 주가가 그대로 표시되어 있습니다.

## 1. 프로젝트 개요
* **프로젝트 이름:** MyStockBot
* **한 줄 설명:** GitHub Actions와 파이썬을 활용하여 매일 장 마감 후 관심 종목의 주가 데이터를 자동으로 수집하고 구글 시트에 누적 기록하는 자동화 프로그램
* **유형:** GitHub Actions 기반 인프라 + 파이썬 배치 스크립트
* **난이도:** 중 (구글 Sheets API 연동 및 웹 크롤링 예외 처리 필요)

## 2. 사용자 시나리오
* **대상 사용자:** 매일 직접 주가를 확인하고 엑셀에 타이핑하는 번거로움을 줄이고, 자동으로 투자 자산의 주가 트렌드를 축적하고 싶은 국내 주식 투자자.
* **시나리오:**
    1. 사용자는 구글 시트의 `Dashboard` 탭에 원하는 국내 주식 종목코드(6자리)를 입력합니다.
    2. 평일(월~금) 오후 4시경, GitHub Actions 스케줄러가 자동으로 깨어나 파이썬 스크립트를 실행합니다.
    3. 프로그램은 종목코드를 문자열 타입으로 엄격히 체크하여 네이버 금융에서 당일 종가를 크롤링합니다.
    4. 크롤링된 데이터는 구글 시트의 `StockData` 탭 맨 아래 행에 순차적으로 누적 저장됩니다.
    5. 작업이 끝나면 사용자는 스마트폰 이메일(Gmail) 푸시 알림으로 당일 자동 수집 결과를 리포트 형태로 확인합니다.

## 3. 핵심 기능 목록
* **다중 종목 설정 및 관리:** 구글 시트에 여러 개의 종목 코드를 입력하면 배열 형태로 한 번에 인식하는 기능
* **주가 데이터 수집:** 설정된 다중 종목의 당일 최종 종가를 네이버 금융 모바일 페이지에서 크롤링하는 기능
* **시트 데이터 누적 기록 (Append):** 매일 새로운 행을 추가하여 `[날짜 | 종목코드 | 종목명 | 당일종가]` 데이터를 순차적으로 누적 저장하는 기능 (API 제한을 고려해 Batch Update 방식으로 구현)
* **시간 기반 트리거 및 주말 제외:** 평일(월~금) 지정된 시간에만 자동 실행되는 스케줄러 기능
* **오류 예외 처리:**
    * 주말 및 공휴일 실행 시 데이터를 수집하지 않고 즉시 종료하는 예외 처리
    * 잘못된 종목 코드 입력 또는 특정 종목 크롤링 실패 시, 전체 프로그램이 멈추지 않고 다음 종목으로 넘어가는 `try-except` 방어 로직
* **Gmail 알림 기능:** 데이터 수집 완료 후 성공/실패 여부와 에러 원인을 포함한 HTML 이메일 리포트 발송 기능

## 4. 기술 스택 및 실행 환경
* **실행 환경:** GitHub Actions (무료 클라우드 러너 기반)
* **개발 언어:** Python 3.x
* **핵심 라이브러리:** `requests`, `BeautifulSoup4` (웹 크롤링), `gspread` (구글 시트 API v4 연동)
* **데이터베이스:** Google Sheets
* **보안 관리:** GitHub Secrets (구글 API 인증 키 및 이메일 계정 정보 암호화 저장)

## 5. 화면 구성 (구글 시트 구조)
* **시트 1: `Dashboard` (사용자 입력 화면)**
    * **A열 (종목코드):** 수집할 국내 주식 종목코드 입력 (서식을 반드시 **'일반 텍스트'**로 지정하여 앞자리 `0` 깨짐 방지)
    * **B열 (종목명):** 사용자가 식별하기 위한 종목 이름
* **시트 2: `StockData` (데이터 누적 저장소)**
    * **구조 (1행 헤더 고정):** `[ 날짜 | 종목코드 | 종목명 | 당일종가 ]`
    * GitHub Actions가 작동할 때마다 맨 아래 빈 행(Last Row)에 데이터를 순차적으로 추가

## 6. 상세 기능 명세 (Workflow)
1. **스케줄러 실행:** 한국 시간(KST) 기준 월~금 오후 4시(UTC 오전 7시)에 GitHub Actions 가상 환경이 실행됨.
2. **타입 검증:** `Dashboard` 시트의 종목코드를 읽어올 때, 파이썬의 `.zfill(6)`을 사용하여 무조건 **6자리 문자열(String)** 형태로 변환 및 검증 처리.
3. **크롤링:** 네이버 금융 모바일 주소(`https://m.stock.naver.com/item/{종목코드}/total`)로 요청을 보내 종가 데이터를 파싱.
4. **일괄 기록:** 크롤링 완료된 데이터를 모아 `gspread`를 통해 단 한 번의 API 호출로 `StockData` 시트 하단에 일괄 삽입.
5. **시간대 고정:** 파이썬 코드 내에 `Asia/Seoul` 타임존을 명시하여 시트에 기록되는 날짜가 한국 표준시와 일치하도록 보장.
6. **알림 발송:** 파이썬 `smtplib` 모듈을 이용해 지정된 이메일로 결과 전송.

## 7. 디자인 가이드
* **구글 시트 서식 보호:** 파이썬 코드는 시트에 오직 '값(Value)만 추가'하도록 작성하여, 미리 설정해 둔 시트의 폰트, 정렬, 천 단위 구분 기호(`,`) 서식이 깨지지 않도록 함.
* **가독성 정렬:** 날짜, 종목코드, 종가는 가운데 정렬, 종목명은 좌측 정렬로 지정.
* **HTML 이메일 리포트:**
    * 성공 시: 초록색 텍스트로 `[성공]` 표시 및 수집된 종목 개수 요약.
    * 실패 시: 빨간색 텍스트로 `[오류 발생]` 표시 및 본문에 에러가 발생한 종목 코드와 에러 원인을 표(Table) 형태로 시각화.

## 8. 제약 사항
* **실행 지연 가능성:** GitHub Actions 무료 서버의 특성상 설정한 시간보다 최소 10분~최대 1시간까지 실행이 지연될 수 있음.
* **구글 API 쿼터 제약:** 분당 요청 횟수 제한을 넘지 않도록 데이터를 모아서 한 번에 보내는 '배치 업데이트' 방식이 강제됨.
* **유지보수 리스크:** 네이버 금융의 HTML 웹 구조가 변경될 경우 크롤링 에러가 발생할 수 있으며, 이 경우 파이썬 소스코드의 태그 경로 수정이 필요함.
* **주말 데이터 중복 방지:** 주말(토/일)에는 작동하더라도 데이터를 수집하지 않고 스크립트를 즉시 안전 종료(`sys.exit()`)하는 로직을 소스코드 상단에 배치해야 함.

# [PRD 확장 v2] MyStockBot 웹앱: 3-페이지 대시보드 구조

> 본 확장 명세는 v1(GitHub Actions + 구글 시트 자동 수집 봇)을 기반으로, 이후 실시간 웹 대시보드(React + FastAPI, KIS Open API·yfinance)로 발전한 현재 구현을 반영합니다.
> v1의 자동 수집·시트 기록·이메일 알림 기능은 그대로 유지하며, **웹 프론트엔드의 화면(페이지) 구조를 아래 3개로 재정의**합니다.

## 9. 페이지 구조 개편 (Information Architecture)

기존에는 단일 페이지(`/` = 관심종목 목록)와 상세 페이지(`/stocks/:code`)만 존재했습니다. 이를 **역할이 명확히 분리된 3개 페이지**로 재편합니다.

| 페이지 | 경로(예시) | 역할 | 비고 |
|--------|-----------|------|------|
| **메인 (시장 대시보드)** | `/` | 코스피·코스닥 지수 등 시장 전체 현황을 한눈에 보는 요약 화면 | 신규 |
| **Sub1 (관심종목)** | `/watchlist` | 개별 종목을 등록·검색·조회하고 상세 판정을 확인하는 화면 | 기존 대시보드 기능 이전 |
| **Sub2 (모의 투자)** | `/paper` | 가상 자본으로 매수·매도를 시뮬레이션하는 화면 | 신규 |

* 상세 화면(`/stocks/:code`)은 Sub1의 하위 화면으로 유지합니다(종목 카드 클릭 → 상세 판정·캔들차트).
* 하단 또는 상단에 3개 페이지를 오가는 **탭 네비게이션(GNB)**을 배치합니다. 모바일(PWA) 우선이므로 하단 탭바 형태를 권장합니다.

> **짚고 넘어가야 할 분석 및 피드백 (구조 개편 시 주의점)**
> 현재 `/`(루트) 경로가 곧 관심종목 목록입니다. 메인 페이지를 신설하면서 루트 경로의 의미가 "관심종목"에서 "시장 대시보드"로 바뀝니다. 기존 링크·PWA 시작 URL·즐겨찾기가 관심종목을 가리키고 있었다면, 라우팅 변경 시 **리다이렉트 또는 온보딩 안내**로 사용자 혼란을 줄여야 합니다.

## 10. 메인 페이지 명세 — 시장 대시보드 (확정)

**목적:** 앱을 열자마자 "오늘 시장이 어떤 상황인가"를 3초 안에 파악하게 한다.
**대상 기기:** 모바일 PWA 우선(세로 스크롤), 하단 3-탭 네비게이션.
**색상 규칙:** 상승 = 빨강, 하락 = 파랑(국내 관례). 브랜드 액센트 = 앰버 골드(상승/하락 의미색과 분리). 실시간 표시 = 그린. 라이트/다크 테마 모두 지원.

### 10.1 화면 레이아웃 (위→아래 확정 순서)
> 시각화 목업으로 배치를 확정함(2026-07 리뷰). 각 블록의 우선순위(Tier)는 '13. 추천 확장 기능'과 연동.

1. **앱 헤더** — 로고 + "MyStockBot" + **실시간 배지**(WebSocket 연결 시 그린 펄스)
2. **시장 상태 줄** — `장전/장중/장마감/휴장` 배지 + "마감까지 N시간 M분" + 마지막 갱신 상대시간
3. **지수 카드 2개(핵심·Tier1)** — 코스피·코스닥을 좌우로. 각 카드: 현재지수 / 전일 대비 등락폭(±)·등락률(%) / **당일 흐름 스파크라인**(면적 채움 + 끝점 강조)
4. **시장 폭(Breadth·Tier2)** — 상승·보합·하락 종목 수 비율 바 + 상한가/하한가 개수 (코스피+코스닥 합산)
5. **투자자 매매동향(Tier2)** — 외국인/기관/개인 순매수(+)·순매도(−) 다이버징 바, 단위 억원
6. **내 관심종목 시그널(Tier1)** — 판정 분포 스트립(강력매수/매수/관망/매도/강력매도) + 종목 수. 기존 `DistributionStrip` 재사용
7. **관심종목 Top Movers(Tier1)** — 당일 급등·급락 상위 3종목 미니 리스트(종목명·코드·판정 배지·등락률) → 탭 시 Sub1 상세로 이동
8. **매크로 참고(선택)** — 원/달러 환율, 나스닥(전일) 등. "참고용·전일 기준" 라벨 명시
9. **디스클레이머 푸터** — "기계적 참고 지표 · 투자 권유 아님"

### 10.2 구성 요소별 상세
* **지수 카드:** 등락 부호(▲/▼)와 색을 동시에 사용해 색맹 접근성 보완. 스파크라인은 당일 인트라데이 시계열.
* **시장 상태 배지:** KST 기준 계산. 휴장(주말·공휴일)일 때는 "최근 거래일 기준" 안내로 데이터 신선도 오해 방지.
* **시그널 분포·Top Movers:** 기존 종목 스냅샷(`snapshot`) 데이터를 그대로 활용하므로 추가 데이터 소스 불필요.
* **매크로:** yfinance로 조회. 실시간이 아니므로 반드시 "참고용" 라벨.

> **짚고 넘어가야 할 분석 및 피드백 (지수 데이터 소스)**
> 코스피/코스닥 **지수**·**시장 폭**·**투자자 매매동향**은 개별 종목 시세와 KIS TR ID가 다릅니다. 각각 별도 조회 함수와 캐시가 필요하며, 기존 종목 스냅샷 캐시(`snapshot_cache`)와 동일한 패턴으로 **지수/시장 전용 캐시**를 두고 주기 갱신하는 구조를 권장합니다.
> * **KIS Open API:** 국내업종 현재지수, 등락종목수, 투자자별 매매동향 API 활용.
> * **yfinance 폴백:** `^KS11`(코스피)·`^KQ11`(코스닥), 환율·해외지수. 지연·결측이 있어 폴백/참고용.

## 11. Sub1 페이지 명세 — 관심종목 (기존 기능 이전)

**목적:** 개별 종목을 넣고 보는 화면. 현재 대시보드 기능을 그대로 이전한다.

* **종목 검색/추가:** 종목명·코드로 검색(`/api/stocks/search`) 후 관심종목에 추가.
* **관심종목 카드 목록:** 종목별 현재가, 등락률, 단기/장기 판정, 실시간 틱(WebSocket) 표시.
* **정렬·필터:** 판정순 / 등락률순 / 이름순 정렬, 검색어 필터.
* **판정 분포 스트립:** 등록 종목의 매수/매도 판정 분포 요약.
* **상세 화면 연동:** 카드 클릭 시 `/stocks/:code` 상세(팩터 분해, 볼린저·RSI·MACD, 멀티 타임프레임 캔들차트)로 이동.
* **삭제:** 관심종목 제거(`DELETE /api/watchlist/{code}`).

> 이 페이지는 **신규 개발이 아니라 기존 `DashboardPage`의 이전**입니다. 라우팅 경로만 `/` → `/watchlist`로 바꾸고 컴포넌트를 재사용하면 됩니다.

## 12. Sub2 페이지 명세 — 모의 투자 (Paper Trading)

**목적:** 실제 돈을 쓰지 않고, 실시간 시세를 기준으로 매수·매도를 연습하며 판정 지표의 유효성을 체감한다.

### 12.1 필수 기능
* **가상 계좌(시드머니):** 최초 진입 시 기본 가상 자본 지급(예: 10,000,000원). 초기 금액은 설정 가능.
* **매수 주문:** 관심종목/검색 종목을 선택 → 수량(또는 금액) 입력 → **현재 시세 기준 즉시 체결**(시장가 시뮬레이션). 잔액 부족 시 거부.
* **매도 주문:** 보유 종목의 수량을 선택해 현재가로 매도 체결. 보유 수량 초과 매도 거부.
* **보유 포트폴리오:** 종목별 보유수량, 평균 매입단가, 현재가, 평가금액, **평가손익(±)·수익률(%)** 표시. 현금 잔액과 총 평가자산 합계 노출.
* **거래 내역:** 일시·종목·매수/매도·수량·체결가·금액을 시간순으로 기록.
* **초기화:** 가상 계좌를 초기 상태로 리셋.

### 12.2 추천 기능
* **자산 추이 그래프:** 총 평가자산의 일별 변화를 라인 차트로 시각화.
* **수익률 랭킹/요약:** 실현손익 vs 평가손익 구분, 최고 수익·최대 손실 종목 하이라이트.
* **판정 대비 성과:** "강력매수 판정 종목을 샀을 때의 가상 수익률" 같은 회고 지표로, v1의 판정 로직 유효성을 검증.

> **짚고 넘어가야 할 분석 및 피드백 (체결·데이터 정합성)**
> * **체결 기준가:** "시장가 즉시 체결"은 구현이 단순하지만, 장 마감·휴장 시 마지막 종가로 체결됩니다. 장중/장외 여부에 따라 체결 가능/불가를 명확히 하고, 체결가의 출처(실시간 틱 vs 종가)를 거래 내역에 함께 기록하는 것을 권장합니다.
> * **호가·수수료:** 실거래의 호가 단위·거래 수수료·세금은 초기 버전에서 생략(단순화)하되, "모의 투자는 수수료·슬리피지를 반영하지 않는다"는 안내 문구를 반드시 노출해 실제 수익률과의 괴리를 오해하지 않도록 합니다.
> * **저장 위치:** 가상 계좌·보유·거래 내역은 서버측 영속 저장(기존 watchlist와 동일한 저장소 패턴)을 권장. 브라우저 로컬 저장만 쓰면 기기 변경 시 데이터가 사라집니다.

## 15. 차별화 전략 — "써야만 하는 이유"

### 15.1 현황 진단
* **상대적으로 강한 것:** 자체 **기계적 종합 판정 로직**(`src/indicators.py`의 단기 60분봉·장기 일봉 5단계 판정)과 **판정 근거의 팩터별 점수 분해**(`web/src/utils/factorScoring.ts` + `FactorBreakdown.tsx`). 국내 리테일 앱에 드문 자산.
* **약한 것(따라잡기):** 실시간 틱·멀티 타임프레임 캔들·지수 대시보드·모의투자 그 자체 — 트레이딩뷰/MTS/토스증권이 구조적으로 더 잘하는 영역. 차별화 엔진이 아니라 기본기.
* **결론:** 현재 "써야만 하는 이유"는 약함. **자체 판정 로직 + 이미 누적 중인 캔들 이력(`db.candles`) + 팩터 분해 + 모의투자**를 엮어 "**판정의 신뢰성·설명·검증**" 계층으로 올라서야 함.

### 15.2 ⭐ 시그니처 기능 — 판정 백테스트 ("이 앱 판정대로 샀으면?")
* **정의:** 종목별로 과거 각 시점에 판정 로직을 재적용해 **적중률·가상 누적 수익률·평균 수익**을 카드/차트로 제시. 예: "최근 1년간 장기 판정을 그대로 따랐다면 가상 누적 +X%, 적중률 Y%".
* **실현 가능성(높음):** `db.candles`에 OHLC 이력이 이미 read-through로 누적 중 → 과거 df 슬라이스에 기존 판정 함수(`macd_cross_signal`/`rsi_zone_signal`/`short_term_view`/`long_term_view`)를 재호출. 체결·손익은 모의투자(Sub2) 체결 로직 재사용. **신규 외부 데이터 소스 0개.**
* **범위 주의:** 재무 지표(PER/PBR/ROE)의 과거값은 결측이 많으므로, **초기 버전은 기술적 판정 백테스트로 한정** 출시. "과거 성과는 미래를 보장하지 않으며 수수료·슬리피지 미반영" 디스클레이머 필수. 종목당 재적용 표본이 적으면 "적중률 X%"가 통계적으로 무의미할 수 있으므로 표본 수·기간 병기.

### 15.2b 경쟁 현황 — 정직한 진단 (2026-07 실증 조사)
> **주의:** "이 기능은 어디에도 없다 / 자체 IP라 복제 불가"는 **사실이 아니다.** 4개 경쟁 카테고리(국내 MTS·국내 퀀트·글로벌 등급·글로벌 소비자앱)를 웹 근거로 조사하고 적대적 검증한 결과, 판정=`partially-exists`(글로벌 거의 존재 / 국내 드묾)로 나왔다.

* **글로벌 — "자체 판정 + 그 판정의 과거 성과 공개 + 개인 노출"은 이미 상용화됨:**
    * **Zacks Rank**: 1~5등급 + "Rank #1대로 샀다면 1988년~ 연 +23.5%" 무료 공개
    * **TipRanks Smart Score**(1~10) / **Seeking Alpha Quant**(5단계): 등급별 과거 성과 공개
    * **Danelfin**(AI Score 1~10) / **Tickeron**: 자체 AI 등급 + 백테스트 승률·수익률을 초보에게 노출
    * **TradingView**: 자체 Technical Rating을 **Strategy Tester로 종목별 과거 재적용**까지 지원(재적용 발상 자체가 이미 존재)
* **국내 — 드묾(rare):** 조사한 한국 앱 중 "자체 5단계 종합 판정 + 종목별 백테스트 + 초보 원탭"을 그대로 결합한 곳은 없음. 증권사 MTS는 대부분 셀사이드 컨센서스 노출(키움 신호검색이 개별 기술신호로 근접), 퀀트 서비스(젠포트·인텔리퀀트·퀀트킹)는 백테스트 대상이 "사용자 전략"이지 앱 자체 판정이 아니며 초보 원탭 아님, 로보(콴텍·파운트·핀트)는 위탁운용이라 자가검증 도구가 아님.
* **진짜 차별점(정직한 버전):** "세계 최초/유일"이 **아님.** 우리가 다른 건 **결합·패키징**뿐 — *"관심종목 개별 종목에 기술적+밸류 5단계 판정을 재적용한 종목별 적중률을, 한국 종목 대상으로, 초보에게 원탭으로"*. 이는 기술 해자가 아니라 UX·로컬라이징 차이.
* **방어 해자 재정의:** 기능 자체는 non-defensible(대형사가 3~6개월 내 유사 탑재 가능, 시세 데이터는 토스·키움이 더 우위). 실제 방어선은 → **① 초보 원탭 UX 완성도 ② 한국 종목·회계·세제 로컬라이징 ③ 판정 룰의 라이브 실적 트랙레코드 축적 ④ 브랜드·유저 선점.** 포지셔닝을 "복제 불가"가 아니라 **"먼저, 제대로, 국내 초보 맞춤으로 선점"**으로 잡아야 정직하다.

### 15.2c 🚀 그로스 기능 — 적립식 백테스트 (DCA 시뮬레이터) + 공유 카드
> 판정 백테스트(§15.2)가 **신뢰·리텐션**용이라면, 적립식 백테스트는 **바이럴 획득(top-of-funnel)**용이다. 쇼츠·릴스에서 흔한 *"10년간 매달 1주씩 샀다면 지금 +N%"* 포맷을 앱 기능으로 제품화한다.

* **정의:** 판정 로직 **없이** 정기 매수만 시뮬레이션. 사용자가 종목·주기·방식·기간을 고르면 "누적 수익률 +N%, 투자 원금 X원, 평가금액 Y원, 수익 Z원"을 **공유 카드(쇼츠 세로 포맷)**로 출력.
* **입력:**
    * 종목/지수 (예: 나스닥100·삼성전자·S&P500)
    * 매수 주기 — 매주 / 매월 / 매분기
    * 매수 방식 — **정량(매월 1주씩)** / **정액(매월 N원어치, 소수점 체결 시뮬)**
    * 기간 — 3/5/10년 또는 커스텀
    * 배당 재투자 ON/OFF
* **출력(공유 카드):** 히어로 수익률(+N%), 원금·평가금액·수익, 평가금액 vs 누적 원금 시계열(면적+기준선), 매수 횟수·평균단가·기간, 브랜드·면책 문구, "내 종목으로 해보기" CTA, 원탭 이미지 공유.
* **왜 그로스에 강한가:** 판정을 몰라도 이해되는 초직관 포맷 → SNS 공유·유입 유도. 카드에 앱 브랜드/CTA가 박혀 **자연 유입 루프**가 된다.
* **실현 가능성(중):** 계산은 DCA라 매우 단순(매 주기 매수→누적 주수·원가→최신가 평가). **단, 장기 월봉 데이터가 선결.** `db.candles`는 read-through로 앞으로만 누적되어 10년치가 아직 없음 → **국내는 KIS 월봉(수정주가), 해외·지수는 yfinance**(`QQQ`·`^NDX`·`^GSPC`)로 장기 시계열을 조회해야 함.
* **정직한 가정·한계(카드에 명시 필수):** 수수료·세금·슬리피지 미반영 / 수정주가(분할·병합 반영) / 배당 재투자 vs 가격수익 구분 / **해외는 환율 영향 포함(달러 기준 별도 표기)** / 과거 성과는 미래 보장 아님 + 시작 시점 민감.

### 15.3 보조 차별화 기능
* **판정 근거 자연어 브리핑:** 점수 바를 한 문장으로 자동 요약("장기 매수: ROE 18%(+1)·PBR 0.8배(+1)·MACD 골든크로스(+2) → 총 +4점"). `buildFactorRows` 결과 재사용, 난이도 하.
* **판정 전환 알림 엔진:** "강력매수 진입", "관망→매수 전환", "RSI 30 이하" 등 사용자 규칙 충족 시 알림. `collector`가 이미 전 종목 판정을 주기 산출 → 직전 사이클과 diff. v1 `notifier` + 웹 푸시 재사용.
* **판정 전환 타임라인(Signal History):** 종목 상세 캔들차트 위에 매수/매도 전환 시점 마커 오버레이. 시그니처 기능의 시각적 프론트엔드.
* **초보자 코칭 모드:** 지표 용어 툴팁 사전 + 판정 5단계 의미 설명. "지표를 몰라도 쓰는 판정 앱" 포지션.

### 15.4 포지셔닝 태그라인(후보)
1. **"판정하고, 증명한다."** — 근거와 과거 성적표까지 보여주는 국내주식 판정 앱
2. **"이 앱 말대로 샀으면?"** — 판정을 백테스트로 검증하는 주식 코치
3. **"왜 사야 하는지까지 알려주는 종합 판정."**

### 16.1 P0 (치명/필수)
* **KIS 토큰/approval_key 캐시 동시성 락:** `src/kis_auth.py`의 `_TOKEN_CACHE`/`_APPROVAL_KEY_CACHE`가 락 없는 dict → 부팅·만료 직후 콜드미스 시 여러 스레드(candles 요청·WS·collector·크론)가 동시에 발급 → KIS 발급 rate-limit(EGW00133) 실패. **double-checked locking**(전역 `threading.Lock`)으로 발급 구간 보호 + rt_cd/error_code 검사 백오프. 지수 API 등 신규 기능의 선결 조건.
* **`bar_history` 데이터 흐름 정리:** `db.save_daily_bars()`의 유일 호출자가 백필 스크립트뿐이고 상시 서버·크론이 적재하지 않아 서버 `bar_history`가 고아 상태(`db.get_bar_history()`는 실질 死코드). 죽은 코드 제거 **또는** collector 사이클에서 일봉 적재 연결. 데이터 소유 경계 문서화(시트=크론 리포트, SQLite=웹앱).

### 16.2 P1 (중요)
* **WebSocket read 워치독:** `kis_ws._read_loop`가 `async for`로 무기한 대기 + `ping_interval=None` → TCP half-open/PINGPONG 중단 시 좀비 연결(배지는 초록인데 틱 없음). `asyncio.wait_for(recv, timeout)` 기반으로 무수신 시 강제 재연결(PINGPONG 주기 2배 기준, 장외 오탐 방지).
* **테스트·린트·타입체크·CI 도입:** 저장소에 테스트/린트/타입설정 0개. 파서(`kis_ws` 46필드 청킹)·지표·`_normalize_code` 단위테스트 + `ruff`/`mypy`/`tsc --noEmit`/`vite build` PR CI 잡. 의존성 상한 핀(현재 `>=` 미고정).
* **모의투자 주문 원자적 트랜잭션(신규 선결):** `db.py`가 호출마다 새 연결·문장별 commit → `POST /api/paper/orders`의 read-modify-write가 동시 주문 시 TOCTOU 레이스(초과매수/음수 잔액). `BEGIN IMMEDIATE` 단일 트랜잭션으로 검증·갱신 원자화. 체결가 출처·장중/장외 함께 저장, **서버측 영속(localStorage 금지)**.
* **지수 전용 수집 루프/캐시(신규 선결):** 지수·등락종목수·투자자 매매동향은 개별 종목과 다른 KIS TR ID → `collector.py` 패턴 복제한 `indices_cache` + `GET /api/indices`. 종목보다 긴 갱신 주기(장중 30~60초), 토큰 락(P0) 선행.

### 16.3 P2 (개선)
* **휴장일 인지:** `collector._is_market_hours`가 평일·시간만 판단, 공휴일 미인지 → 불필요 조회 + "휴장" 배지 데이터 근거 부재. 공휴일 캘린더 도입.
* **KIS rate-limit 전역 조율:** `KIS_RATE_LIMIT_DELAY`가 스레드 로컬 `sleep`인데 `ThreadPoolExecutor(max_workers=4)` 병렬 → 초당 버스트가 의도의 수 배. 전역 토큰버킷/세마포어.
* **in-memory 상태 재시작 유실:** collector·재무·소스 캐시가 프로세스 메모리 → 재시작 시 첫 사이클 전까지 빈 스냅샷. 부팅 워밍 또는 프론트에 첫 사이클 지연 명시.
* **보안 인지 항목:** WS 토큰 `?token=` 쿼리 노출(액세스로그), 프론트 `localStorage` 토큰(XSS), 마스터 다운로드 `verify=False`, `/docs` 무인증. 개인용이라 수용 가능하나 문서화 + 프로덕션 문서 라우트 인증/비활성 권장.
* **관측성/헬스체크:** `print()` 산재·타임스탬프 없는 로깅 → 표준 `logging` 통일. 헬스체크가 liveness만 → `/api/health`에 WS 상태·마지막 스냅샷 신선도(readiness) 추가.
* **배포:** 컨테이너 root 실행 → 비특권 유저. 크론 미고정 의존성·무캐시 `pip install` → 핀 + pip 캐시. (`--workers 1`은 in-memory 상태·WS 구조상 필수 = 수평 확장 한계로 명시.)
