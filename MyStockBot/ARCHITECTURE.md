# MyStockBot 설계서

다음 사람(또는 다음 에이전트)이 이 저장소를 이어받을 때 읽는 문서. **왜 이렇게 짰는지**를
남기는 것이 목적이라, 파일 목록보다 설계 결정과 함정에 지면을 쓴다.

기준: `develop` (2026-08) · 백엔드 테스트 622개 · 프론트 19개

---

## 1. 두 개의 실행 경로

이 저장소는 하나의 앱이지만 **서로 독립적인 두 프로세스**로 동작한다. 어느 쪽 결과를 보고
있는지 아는 것이 디버깅의 출발점이다.

| | 웹앱 | 일일 배치 |
|---|---|---|
| 실행 | FastAPI + React PWA (집 PC Docker, 상시) | GitHub Actions 크론 (평일 KST 16:00) |
| 진입점 | `server/main.py` | `src/main.py` |
| 저장소 | SQLite `data/mystockbot.db` | Google Sheets |
| 역할 | 실시간 대시보드·판정·백테스트·모의투자 | 장 마감 스냅샷 누적 + 메일 리포트 |

크론은 러너가 매번 새로 클론되므로 **SQLite 캐시를 못 쓴다** — 휴장일도 하드코딩 표만 본다
(`src/market_calendar.py`). 매년 12월 다음 해 표를 갱신해야 하는 이유가 이것이다.

관심종목은 양방향 동기화(`src/watchlist_sync.py`)로 한 벌처럼 유지된다.

## 2. 계층

```
web/src/            React PWA — 그리기만 한다. 판정 점수를 재계산하지 않는다.
  ├ pages/          화면 5개. **파일명이 직관과 어긋나니 주의**:
  │                   MainDashboardPage → "/"        (메인 대시보드)
  │                   DashboardPage     → "/watchlist" (관심종목)
  │                   PaperTradingPage  → "/paper"
  │                   AlertsPage        → "/alerts"
  │                   StockDetailPage   → "/stocks/:code"
  ├ components/     카드·칩·차트. 백엔드가 준 값을 렌더
  ├ hooks/          useSnapshot(20초 폴링)·useTickStream(WS)·useMarketStatus
  └ utils/          decision.ts(정렬·집계·워밍업 판정)·dcaShare.ts(공유 카드 렌더)

server/             FastAPI — HTTP 계약과 오케스트레이션
  ├ routers/        얇게 유지. 검증 → 서비스 호출 → 스키마로 직렬화
  ├ services/       비즈니스 로직 전부. 아래 §3 참조
  ├ schemas.py      Pydantic 응답 계약. 확장은 항상 additive(기본값 있는 필드)
  ├ auth.py         단일 토큰 + 브루트포스 감속기
  └ errors.py       SQLite 쓰기 경합 → 429 변환

src/                크론 배치와 웹앱이 **공유**하는 순수 모듈
  ├ db.py           SQLite 전부. 스키마·마이그레이션·모든 쿼리
  ├ indicators.py   MACD/RSI/볼린저/눌림목. 순수 함수, 외부 I/O 없음
  ├ decision_rules.py  판정 점수표·임계값의 단일 소스
  ├ crawler.py      KIS REST + yfinance 수집
  ├ kis_auth.py     토큰·approval_key 발급, 전역 호출 스로틀
  └ market_calendar.py  장 상태·거래일 계산
```

**의존 방향은 한 방향이다**: `web → server → src`. `src/`는 `server/`를 절대 import 하지
않는다 — 크론 배치가 FastAPI 없이 돌아야 하기 때문이다.

## 3. 서비스 지도

`src/` 소속(크론과 공유)과 `server/services/` 소속(웹앱 전용)을 구분해 둔다 — 전자를
고치면 크론 배치까지 영향받는다.

| 모듈 | 위치 | 하는 일 | 특이점 |
|---|---|---|---|
| `collector.py` | `server/services/` | 상시 수집 루프(장중 30초·그 외 600초) | 유일한 백그라운드 쓰기 주체. 판정·알림의 원천 |
| `candles.py` | `server/services/` | 멀티 타임프레임 캔들 read-through | **모든 캔들 쓰기의 관문**(§5) |
| `snapshot_cache.py` | `server/services/` | collector 상태 → API 응답 변환 | 계산 없음. 순수 변환 |
| `alerts.py` | `server/services/` | 판정 전환 알림 게이트 | 오알림 방지 장치 6종(§6) |
| `kis_ws.py` | `server/services/` | KIS 실시간 체결가 중계 | 세션당 구독 41건 상한 |
| `backtest.py` | `server/services/` | 판정 재적용 적중률 | 재무 제외(과거 재현 불가) |
| `dca.py` / `whatif.py` | `server/services/` | 적립식·타임머신 시뮬레이션 | 판정 로직 미사용, 가격만 |
| `paper.py` | `server/services/` | 모의투자 + 자산 추이 | 체결가는 collector 스냅샷 |
| `rule_eval.py` | `server/services/` | 룰 평가 하네스(CLI) | 가중치를 바꿀 **근거가 있는지**를 먼저 답한다 |
| `scheduler.py` | `server/services/` | 일일 배치 5개 | 백업 17:00 · 백필 16:20 · 마스터 16:00 · 휴장일 08:10 · 시트임포트 평일 09~15시 매시 :50 |

## 4. 핵심 설계 결정

### 4-1. 판정 규칙은 백엔드에 하나만 둔다

예전엔 프론트(`utils/factorScoring.ts`)가 점수표를 TS로 복제해 다시 계산했고, 그 파일 주석이
"백엔드 점수와 불일치할 수 있다"고 스스로 인정하고 있었다. 즉 **화면에 보이는 근거 합계와
실제 판정이 갈라질 수 있었다.**

지금은 `src/decision_rules.py` 한 곳에서 점수·설명문·임계값을 만들어 응답에 실어 보내고,
화면은 그린다. 새 지표를 더할 때도 이 원칙을 깨지 말 것.

### 4-2. '강력' 등급은 기술 지표 확증을 요구한다

재무 점수 최대치(±3)가 장기 강력 임계값(3)과 같아서, 확증 규칙이 없으면 **PER·PBR·ROE만으로
기술 신호 없이 '강력매수'**가 나왔다. 기술 점수가 같은 방향으로 |1| 이상일 때만 강력을 준다.

지표가 결측일 때 그것을 "중립 확증"으로 오독하지 않는 것이 핵심이다.

### 4-3. 수집(쓰기)과 제공(읽기)을 분리한다

API 핸들러는 외부를 호출하지 않는다 — collector가 SQLite에 써 두면 핸들러는 읽기만 한다.
차트(`candles.py`)만 예외로 read-through를 하는데, 타임프레임 조합이 너무 많아 미리 다 받을
수 없기 때문이다. 그 경로도 블로킹이라 `asyncio.to_thread`로 넘긴다.

### 4-4. 실시간은 표시 전용이다

WebSocket 틱은 화면의 가격만 덮어쓰고 **판정 계산에는 들어가지 않는다**(판정은 확정 봉 기반).
장중 판정이 마감까지 바뀔 수 있다는 성질은 게이트로 없앨 수 없어서, 알림 본문에 그 사실을
문구로 붙인다.

### 4-5. 데이터 없음은 예외가 아니다

상장 전 구간, 빈 캔들, 미수집 종목은 **200 + 빈 결과 또는 error 필드**로 내려간다.
422는 입력이 틀렸을 때(형식·미래 날짜), 409는 이력이 계산에 못 미칠 때만 쓴다.

## 5. 캔들 저장의 관문 — `candles.store_candles`

캔들을 쓰는 경로는 여럿이지만(차트 요청·수집 루프·백필) **저장은 한 함수를 통과한다.**
지수(`^KS11`)만 예외인데 yfinance 단일 소스라 아래 두 위험이 없기 때문이다.

관문이 막는 것:

1. **조정 규약 혼합** — KIS는 원주가(정수), yfinance는 `auto_adjust=True`(분할·배당 조정)다.
   같은 `(code, tf, t)` PK에 번갈아 덮이면 한 종목 안에서 기준가가 갈린다. `source` 컬럼으로
   규약을 기록하고, 다른 소스로 바뀌면 그 `(code, tf)`를 통째로 비우고 새로 채운다.
2. **분할 단차** — 액면분할이 나면 원천은 과거 전체를 재조정해 주지만, 최근 구간만 덮으면
   **경계 불연속이 영구화**된다(깊이 게이트가 "충분하다"고 보고 더 파지 않으므로).
   `timeseries.detect_split_anomaly`로 감지해 전량 재적재한다.

> 캔들은 소스에서 재구축 가능한 캐시다 — 잘못된 가격을 남기는 것보다 지우고 다시 받는 편이
> 낫다. 이 판단이 관문 설계의 전제다.

**아직 안 한 것**: KIS 호출이 `FID_ORG_ADJ_PRC="0"`(원주가) 고정이다. `"1"`(수정주가)로
바꾸려면 이 저장소의 "KIS 파라미터는 공식 코드 교차확인 후에만" 관례를 따라야 한다. 규약
기록이 이미 들어갔으므로, 전환하면 `source` 변화가 자동으로 전량 재적재를 유발한다.

### 깊이 게이트와 비용 방어

차트가 과거를 요구하면(일봉 1000봉 ≈ 4년) 저장소가 얕을 때 KIS 페이지네이션으로 판다.
무한 재수집을 세 겹으로 막는다:

- **쿨다운** 600초 — 원천이 얕은 종목(신규상장)이 매 요청마다 파는 것을 막는다
- **원천 고갈 바닥**(`candle_history_floor`) — "여기가 상장 시작점"을 기억. `kis` 확인분의
  1d/1w/1M만 영속화한다. yfinance 폴백(2년)을 굳히면 그 종목 일봉이 2년에서 영구히 잘린다
- **30일 재검증 TTL** — 바닥은 "더 없다"는 **부정 확인**이라 스스로 풀리지 않는다(바닥이 딥
  수집을 막고, 딥 수집이 없으면 바닥을 내릴 관측도 없다). 한 달에 한 번 무시하고 재확인한다

## 6. 알림 게이트 — 각각이 실제로 겪은 오알림이다

`alerts.py`의 게이트는 장식이 아니라 사고 기록이다.

| 게이트 | 막는 것 |
|---|---|
| 판정 없음 무시 | 수집 실패(None)·데이터부족이 매매 신호로 보이는 것 |
| 기준선 = 마지막 **알린** 판정(SQLite 영속) | 재시작마다 전 종목 알림 폭발 / A↔B 왕복 시 매번 알림 |
| 입력 구성 변화 시 무음 재시딩 | 재무데이터가 뒤늦게 도착해 장기 판정이 ±3점 통째로 이동 |
| 히스테리시스(2사이클 확정) | 경계에서 떨리는 판정 |
| 쿨다운 60분 | 같은 종목의 연속 알림 |
| 장 시간대 한정 | 장외 데이터로 인한 알림 |
| 발송 **성공 시에만** 기준선 이동 | 발송 실패한 전환이 조용히 사라지는 것 |

60분봉이 35봉에 못 미칠 때 지표가 '데이터부족'이 아니라 **0점=관망**을 내는 성질도 여기서
방어한다 — 35번째 봉이 쌓이는 순간 가짜 '관망→매수' 전환이 생기기 때문이다.

## 7. 함정 모음

이걸 모르면 반드시 한 번은 밟는다.

- **KIS 분봉 종가는 `stck_prpr`** 이다. 일봉의 `stck_clpr`을 재사용하면 전 종목 close가 None이
  된다. 파서를 공유하지 않고 분리한 이유.
- **KIS 기간별시세는 호출당 100건** — 페이지네이션 없이는 일봉이 5개월에서 잘린다.
- **`kis_throttle()`이 전역 직렬화**를 건다(0.5초). ThreadPoolExecutor 병렬성과 무관하게
  프로세스 전체에서 순서화되므로, 종목 수가 늘면 콜드 사이클이 선형으로 길어진다.
- **WS 구독 41건 상한** — `load_watchlist`가 추가 순이라 **가장 최근에 추가한 종목**이 잘린다.
  status 프레임의 `excluded`로 화면에 알린다.
- **미들웨어 순서** — CORS를 나중에 `add_middleware` 해야 최외곽이 되어 401 응답에도 CORS
  헤더가 붙는다. 반대면 브라우저가 401 본문 대신 CORS 에러를 본다.
- **SQLite는 WAL + busy_timeout 5초**. 그래도 넘치면 `errors.py`가 429로 바꾼다(500 아님).
  락 판별은 문자열이 아니라 `sqlite_errorcode`로 한다.
- **UTC/KST 경계** — `paper_trades.ts`는 UTC 저장, 캔들 `t`는 KST 자정 기준 epoch다.
  같은 축에 놓으려면 변환이 필요하다(자산 추이가 이걸 한다).
- **마스터 파일이 잘려도 zip은 열린다** — 행 수만 줄어든 채 성공하므로, 상폐 판정 전에
  시장별 절대 하한과 기존 대비 95% 가드를 통과시킨다.
- **프론트에서 `toISOString()`은 UTC다** — 서버가 KST로 해석하는 날짜에 쓰면 해외 접속 시
  하루가 어긋난다. `toLocaleDateString("en-CA", {timeZone:"Asia/Seoul"})`을 쓴다.

## 8. 워밍업 — 비어 보이는 게 정상인 구간

새로 띄우거나 종목을 추가하면 한동안 화면이 빈다. 전부 정상이고, 화면이 그렇게 말하도록
문구를 넣어 뒀다(예전엔 설정 오류처럼 읽혔다).

| 구간 | 얼마나 | 왜 |
|---|---|---|
| 부팅 후 첫 사이클 | 종목당 약 2초 | KIS 3콜 × 전역 스로틀 |
| 종목 추가 후 며칠 | 60분봉 35개까지 | 그 전엔 단기 판정이 '축적 중' |
| 종목 추가 후 하루 | 야간 백필까지 | 백테스트 독립 표본 부족 → '참고치' |
| 알림 켠 뒤 첫 거래일 | 최소 1거래일 | 첫 사이클은 무음 시딩 + 2사이클 확정 + 장중만 |

## 9. 이 앱이 답하지 않는 것

설계 경계를 명시해 둔다 — 이걸 모르면 없는 기능을 찾게 된다.

- **주문을 내지 않는다.** 관측·판정·시뮬레이션까지다. 실주문 엔드포인트가 없다.
- **"무엇을 살까"에 답하지 않는다.** 스크리너·랭킹이 없고, Top Movers도 판정 분포도 전부
  내 관심종목 안의 집계다. 이 앱이 하는 일은 "내가 이미 정한 것을 매일 같은 기준으로 관측"이다.
- **판정 가중치는 검증된 값이 아니다.** 손으로 정한 상수이고, 개인 관심종목 규모에서는
  가중치 조정의 기대효과보다 검출한계가 커서 어느 값이 더 나은지 데이터로 고를 수 없다.
  `rule_eval.py`가 그 사실을 직접 알려주며, 정직한 결론은 "근거가 없으므로 현행 유지"다.

## 10. 작업 규약

- **테스트는 목보다 실물을 쓴다** — DB는 `tmp_path`의 실제 SQLite, 외부 HTTP만 monkeypatch.
  마이그레이션·PK 충돌·트랜잭션 경계는 목으로 검증되지 않는다.
- **스키마 확장은 additive** — 기본값 있는 필드로 더한다. 구버전 응답을 받는 화면이 깨지면 안 된다.
- **모르는 것을 안다고 적지 않는다** — 마이그레이션에서 기존 행을 그럴듯한 값으로 채우지 말고
  NULL로 둔다(`candles.source`, `paper_trades.price_source`가 그 예).
- **KIS 파라미터는 공식 코드 교차확인 후에만** 건드린다. 근거를 주석에 파일·라인까지 남긴다.

  `node scripts/smoke_ui.mjs <URL> <TOKEN>`(브라우저)
